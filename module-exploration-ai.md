## 3. What is the Pipfile?

The **Pipfile** is Python's modern dependency management file that specifies all the packages (libraries) required by this Django project. It's similar to `package.json` in Node.js projects.

It declares dependencies organized into:
- `[packages]` — Production dependencies needed to run the live application
- `[dev-packages]` — Development-only dependencies for testing, debugging, and code quality

The Pipfile pins specific or minimum versions for packages to ensure consistency across development, testing, and production environments. It works with `Pipenv` (a dependency management tool) to create isolated Python environments, preventing conflicts between project dependencies. The Pipfile ensures every developer and production environment has the exact same dependencies, preventing "works on my machine" issues and making the project reproducible.

For this project, production packages include Django, REST framework, database drivers, logging tools, and a production web server (gunicorn). Development packages include testing frameworks (pytest), debugging tools (debugpy), and code quality tools (pylint).

## 5. What does `decorators.py` do?

**Decorators** are Python functions that modify or enhance other functions without permanently changing them. They wrap a function to add extra functionality before or after it executes. A decorator is applied using the `@decorator_name` syntax above a function.

`decorators.py` contains two authorization decorators that implement role-based access control:

1. **`@is_instructor()`** — Restricts API endpoints to users in the "Instructors" group
   - Checks if `request.user.groups` contains "Instructors"
   - If yes: executes the decorated function normally
   - If no: returns a 401 Unauthorized response with message "You must be an instructor"

2. **`@is_staff()`** — Restricts API endpoints to users in the "Staff" group
   - Same logic but checks for "Staff" group membership
   - Returns 401 Unauthorized if user is not in staff group

**How they're used:**

These decorators protect endpoints so only authorized users can access them. For example:
```python
@is_instructor()
def some_endpoint(request):
    # This code only runs if user is an instructor
```

This ensures students can't access instructor-only features like creating assessments or viewing all students' grades. They're a security mechanism preventing unauthorized access to sensitive operations.


## 6. What is a serializer, and how does it fit the request/response cycle?

**What is a serializer?**

A serializer is a Django REST Framework component that converts between Python objects (like database models) and JSON data. It acts as a translator between the API client (JavaScript frontend) and the Python backend.

**Purpose:**

Serializers serve two main purposes:
1. **Serialization** — Convert Python model instances into JSON to send to the client (Response)
2. **Deserialization** — Convert incoming JSON from the client into Python objects to save to the database (Request)

**How they work:**

In this project, serializers are defined as simple `ModelSerializer` classes that inherit from `serializers.ModelSerializer`. For example:

```python
class NssUserSerializer(serializers.ModelSerializer):
    class Meta:
        model = NssUser
        fields = ('url', 'slack_handle', 'github_handle', 'mentor', 'user')
```

The `Meta` class specifies:
- `model` — Which Django model to serialize (NssUser, Cohort, Capstone, etc.)
- `fields` — Which model fields to include in the JSON output

**The Request-Response Cycle:**

1. **Client sends request** — Browser sends JSON data: `{ "name": "Cohort 1", "startDate": "2025-01-01" }`

2. **Django receives request** — The view receives this JSON in `request.data`

3. **Deserialization** — If using a serializer, it converts the JSON into a Python object that matches the model structure

4. **Process** — View logic creates/updates the database model, performs business logic

5. **Serialization** — When returning data, the serializer converts the Python model instance back into JSON

6. **Response sent** — API returns JSON: `{ "id": 1, "name": "Cohort 1", "startDate": "2025-01-01" }`

**Why serializers matter:**

- **Validation** — Serializers can validate data before saving to database
- **Security** — Control which fields are exposed to clients (e.g., hide internal fields)
- **Consistency** — Ensure all API responses have the same JSON structure
- **Less code** — Automatic conversion without manual JSON parsing

**In this project:**

Files like `nssuser_serializer.py`, `cohort_serializer.py`, and `capstone_serializer.py` define how each model should be formatted for API responses and requests.


## 7. One model and what it represents

**What is a Django Model?**

A Django model is a Python class that represents a single database table. It defines:
- **Fields** — The columns in the database table (like `name`, `start_date`, `active`)
- **Data types** — How each field stores data (`CharField`, `DateField`, `BooleanField`, etc.)
- **Relationships** — How tables link together (`ForeignKey`, `OneToOneField`, `ManyToMany`)
- **Methods and properties** — Custom logic for the model (like `coaches` or `is_instructor`)

Models are Django's way of writing Python code instead of writing SQL directly. When you save a model instance, Django automatically handles the database INSERT/UPDATE. When you query for models, Django handles the SELECT queries.

**Example Model: Cohort**

The `Cohort` model represents a student cohort (class/batch) in the Learning Platform:

```python
class Cohort(models.Model):
    name = models.CharField(max_length=55, unique=True)
    slack_channel = models.CharField(max_length=55)
    start_date = models.DateField()
    end_date = models.DateField()
    break_start_date = models.DateField()
    break_end_date = models.DateField()
    active = models.BooleanField(default=False)
```

**Why the API tracks Cohorts:**

The Cohort model is critical because Nashville Software School runs programs in cohorts (class groups). The API needs to track:

1. **Group identity** — Each cohort has a unique name (e.g., "Python Cohort 52", "Web Cohort 51")
2. **Timeline** — When the cohort starts/ends and when breaks occur (important for tracking student progress and deadlines)
3. **Communication** — The Slack channel for the cohort (for team collaboration)
4. **Status** — Whether the cohort is active (currently running) or archived

**Real-world mapping:**

- **Cohort in the database** = One class/batch of students learning together at NSS
- **cohort.name** = The official name of the class (e.g., "Web Dev 50")
- **cohort.start_date & end_date** = When the 12-week program runs
- **cohort.break_start_date & break_end_date** = When students have holiday breaks
- **cohort.slack_channel** = The Slack workspace where instructors and students collaborate
- **cohort.active** = Is this class currently running, or is it archived?

**Why this matters for the API:**

Without tracking cohorts, the API couldn't organize students into groups, manage different class schedules, or associate assessments with the right students. Every student belongs to a cohort, every course assignment is tied to a cohort's timeline, and instructors need to know which cohort they're working with.


## 8. Views vs. viewsets

**What's the difference?**

A **View** handles a single, specific endpoint with custom logic. A **ViewSet** groups multiple related operations (Create, Read, Update, Delete) for a single resource into one class.

**View Example: `notify()` (Function-based View)**

```python
@api_view(['POST'])
def notify(request):
    """Sends a notification message to a Slack channel."""
    instructors = request.data.get("instructors", None)
    student_channel = request.data.get("studentChannel", None)
    message = request.data.get("message", None)
    
    # Custom logic for sending Slack notifications
    if instructors:
        SlackAPI().send_message(text=message, channel=slack_channel)
        return Response({'message': 'Notification sent'}, status=200)
    return Response({'message': 'Invalid request'}, status=400)
```

- **Purpose**: One specific operation (send Slack notification)
- **Route**: Maps to a single endpoint like `/api/notify/`
- **Logic**: Custom business logic unique to this endpoint

**ViewSet Example: `BookViewSet`**

```python
class BookViewSet(ViewSet):
    """Book view set"""
    
    def create(self, request):      # POST to create a book
    def retrieve(self, request, pk=None):  # GET single book
    def update(self, request, pk=None):    # PUT to update
    def destroy(self, request, pk=None):   # DELETE a book
    def list(self, request):        # GET all books
```

- **Purpose**: All CRUD operations for one resource (Book)
- **Routes**: Automatically generates multiple endpoints:
  - `GET /books/` (list)
  - `POST /books/` (create)
  - `GET /books/{id}/` (retrieve)
  - `PUT /books/{id}/` (update)
  - `DELETE /books/{id}/` (destroy)
- **Shared logic**: All methods can share permissions, serialization, and database access patterns

| Type | Example class | When to use it |
|------|--------------|----------------|
| View | `notify()`, `popular_queries()` | **Custom endpoints** — One specific operation that doesn't follow standard CRUD (sending notifications, running complex queries, custom calculations). Unique business logic that doesn't fit standard resource operations. |
| ViewSet | `BookViewSet`, `CohortViewSet` | **Standard CRUD operations** — When you need to Create, Read, Update, Delete a resource (like books, cohorts, students). Reduces boilerplate code by generating all standard routes automatically. When operations share similar logic and permissions. |

**Why pick one over the other:**

- **Choose View** when you need a single custom endpoint with unique logic (e.g., "send a notification", "get popular search queries", "migrate students between cohorts")
- **Choose ViewSet** when you're building standard CRUD functionality for a database model (e.g., managing books, cohorts, courses)

## 9. What replaces templates and why?

**What replaces templates?**

**Serializers** replace templates in this REST API project.

**Traditional Django (MTV - Model-Template-View):**
- **Model** → Database representation
- **Template** → HTML files that render data for browsers
- **View** → Processes requests and renders HTML templates

**This REST API project (Model-Serializer-View):**
- **Model** → Database representation
- **Serializer** → JSON representation of data (for API clients)
- **View** → Processes requests and returns serialized JSON

**Why serializers make sense for a REST API:**

1. **JSON instead of HTML** — Traditional templates render HTML for humans to view in a browser. Serializers render JSON for machines (other applications, frontend frameworks, mobile apps) to consume programmatically.

2. **Structured data** — JSON is machine-readable structured data with a clear format. The frontend app receives predictable data structures it can parse and use.

3. **No visual rendering needed** — A REST API doesn't render anything for humans to see. It just returns data. There's no need for HTML, CSS, or visual presentation.

4. **Decoupled frontend and backend** — By returning JSON, the backend API can serve any frontend (web, mobile, desktop app). Multiple clients can consume the same API without the backend needing to know about them.

5. **Better for reuse** — The same API endpoint can power a JavaScript frontend, a mobile app, and a third-party integration—all consuming the same JSON response.

**Comparison:**

| Aspect | Templates (Traditional Django) | Serializers (REST API) |
|--------|-------------------------------|----------------------|
| **Output format** | HTML (human-readable) | JSON (machine-readable) |
| **Audience** | Web browsers with users | Other applications/clients |
| **Use case** | Rendering web pages | Providing data to frontend/apps |
| **Presentation** | Includes styling, layout, HTML | Pure structured data |
| **Files** | HTML files in `templates/` folder | Python classes in `serializers/` folder |

**Example flow:**

Traditional Django:
```
User Request → View → Template (renders HTML) → Browser displays webpage
```

REST API:
```
API Client Request → View → Serializer (converts to JSON) → Client parses JSON data
```

This architecture is why this project doesn't have any HTML templates—it's designed to be consumed by frontend applications (like React, Vue, or mobile apps) that make requests to the API and receive JSON responses.
